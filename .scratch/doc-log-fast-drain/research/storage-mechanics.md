# Storage mechanics research

Resolves ticket [01 - Storage mechanics research](../issues/01-storage-mechanics-research.md).
Researched 2026-08-28 against Microsoft Learn, the Azurite GitHub repo, and Serilog GitHub repos/NuGet.

## 1. Azure Append Blob (AppendBlock)

Source: [Append Block (REST API)](https://learn.microsoft.com/en-us/rest/api/storageservices/append-block)

- **Atomicity / concurrency**: each `Append Block` call commits one block atomically to the end of the blob; "the block of data is immediately available after the call succeeds." The docs explicitly describe the **multiple-writer scenario**: uncoordinated writers can all call Append Block safely — the service serializes appends. Caveat: with multiple writers, *ordering and duplicates* (from client retries) are the app's problem; docs recommend "For the highest concurrent append throughput, applications should handle redundant appends and delayed appends in the application layer. For example, the application can add epochs or sequence numbers in the data being appended." (Our design already carries producer timestamps, so retried/duplicate appends are handled at read time.)
- **Max size per AppendBlock call**: 4 MiB for service versions earlier than 2022-11-02; 100 MiB (preview) for 2022-11-02 and later. Oversized block → HTTP **413 Request Entity Too Large**.
- **Block cap**: **50,000 appends max per append blob** — confirmed real. Exceeding it → HTTP **409 Conflict** (error code `BlockCountExceedsLimit` family). Response header `x-ms-blob-committed-block-count` is returned on every append, so a writer can see how close it is and trigger rollover.
- **Max total blob size**: ~195 GiB (4 MiB x 50,000) on older versions; ~4.75 TiB (100 MiB x 50,000) on 2022-11-02+.
- **Conditional headers**:
  - `x-ms-blob-condition-appendpos`: append succeeds only if current blob offset equals the given byte offset; otherwise **412 Precondition Failed** (`AppendPositionConditionNotMet`). Intended for *single-writer* dedupe after network failures — not for multi-writer coordination ("this might not be optimal for performance" with multiple writers).
  - `x-ms-blob-condition-maxsize`: fails with **412** if the append would push the blob past the given max size (`MaxBlobSizeConditionNotMet`).
- **Other**: `Append Block` only works on a blob created with `x-ms-blob-type: AppendBlob` (Put Blob first); calling it on a nonexistent blob errors, so consumers must create-if-not-exists. Block IDs are not exposed; `Get Block List` is invalid on append blobs.

Design implication: at ~100 lines/doc and one append per consumer flush, the 50k-block cap is far away for our workload (a doc would need 50,000 separate flushes). Watch `x-ms-blob-committed-block-count` if rollover ever matters.

## 2. Azure Storage Queue

Sources: [Get Messages (REST API)](https://learn.microsoft.com/en-us/rest/api/storageservices/get-messages), [Scalability and performance targets for Queue Storage](https://learn.microsoft.com/en-us/azure/storage/queues/scalability-targets), [Introduction to Azure Queue Storage](https://learn.microsoft.com/en-us/azure/storage/queues/storage-queues-introduction), [Storage queues vs Service Bus queues compared](https://learn.microsoft.com/en-us/azure/service-bus-messaging/service-bus-azure-and-service-bus-queues-compared-contrasted)

- **Batch size**: `Get Messages` (`ReceiveMessagesAsync` in the .NET SDK) retrieves **at most 32 messages** per call (`numofmessages` range 1-32, default 1). Out-of-range → 400 `OutOfRangeQueryParameterValue`.
- **Visibility timeout**: default **30 seconds**, range 1 second to **7 days**, set per dequeue call. On dequeue the message becomes invisible until `TimeNextVisible` (= retrieval time + visibilitytimeout); the consumer must delete it (via the per-message `PopReceipt`) before then. If not deleted, the message reappears for any consumer — this is the at-least-once redelivery mechanism. Non-guarantees worth knowing: clock skew can make a message reappear slightly early, and if a pop receipt returns **404** the message was re-dequeued by someone else. `Update Message` can extend the timeout (lease renewal) mid-processing.
- **Throughput targets**: up to **2,000 messages/sec per queue** (1 KiB messages) and **20,000 messages/sec per storage account**. Beyond a partition's limit the service returns 503 (Server Busy)/500 — use exponential backoff. Max single queue size: 500 TiB.
- **Message size**: max **64 KiB**. With Base64 encoding (required for non-XML-safe/binary content; `QueueClientOptions.MessageEncoding = QueueMessageEncoding.Base64` in the .NET SDK) the usable raw payload drops to **48 KiB** — matches the "~48KB usable" packing assumption. Quote: "If you Base64-encode the message, the user payload can be up to 48 KB, instead of 64 KB."
- **DequeueCount**: set to **1 on first dequeue**, incremented on each subsequent dequeue of the same message. Standard poison handling (per the comparison doc): "when dequeuing a message the application examines the DequeueCount property... If DequeueCount is greater than a given threshold, the application moves the message to an application-defined 'dead letter' queue." There is no automatic dead-lettering in Storage Queues — the app must do the move (our plan: poison queue after 5 dequeues).
- **Ordering**: not guaranteed FIFO (visibility-timeout expiry reorders); delivery is at-least-once. Both already accepted in the design.

## 3. Azurite fidelity

Sources: [Azurite README (Azure/Azurite)](https://github.com/Azure/Azurite), [Azurite ChangeLog](https://github.com/Azure/Azurite/blob/main/ChangeLog.md)

- Current release: **3.37.0**, Azure Storage API version **2026-06-06**. Docker image: **`mcr.microsoft.com/azure-storage/azurite`** (`docker run -p 10000:10000 -p 10001:10001 -p 10002:10002 mcr.microsoft.com/azure-storage/azurite`; blob 10000, queue 10001, table 10002).
- **Append blobs: supported** since v3.7.0 ("Supported append blob", 2020.04); 100 MiB append block since v3.25.0; CRC-64 checksums for AppendBlock in 3.37.0. Note the blob must be created via the dedicated Create Append Blob path — README: "Put Blob (Create append blob is not supported)" but "Create Append Blob, Append Block" are in the supported list. The .NET `AppendBlobClient.CreateIfNotExistsAsync` uses the right operation, so this is a non-issue for SDK users.
- **Gap: "Concurrent Append" is explicitly listed under "NOT supported or limited supported"** in the blob support matrix. Azurite also states it "is not a scalable storage service and does not support many concurrent clients" with "no performance and TPS guarantee." So heavy uncoordinated multi-writer appends to the *same* blob may behave less faithfully (and much slower) than real Azure. Mitigation for the sim: per-DocGuid blobs mean concurrent same-blob appends only happen when two consumers hold lines for the same doc simultaneously — rare but real; treat 409/412/500s from Azurite appends as retryable and don't read absolute append throughput off Azurite numbers.
- **Queue service: fully supported** — Put Message, Get Messages (incl. batch `numofmessages`), Peek, Delete, Update Message, Clear — the only listed queue gap is SharedKey Lite auth. Visibility timeout and DequeueCount are part of the Get Messages contract Azurite implements at API version 2026-06-06; the Get Messages REST doc itself documents the Azurite endpoint (`http://127.0.0.1:10001/devstoreaccount1/...`). No documented fidelity gaps for visibility timeout, batch dequeue, or dequeue count.

## 4. Serilog (as of 2026)

Sources: [Serilog on NuGet](https://www.nuget.org/packages/Serilog), [Serilog v4.0.0 release notes](https://github.com/serilog/serilog/releases/tag/v4.0.0), [IBatchedLogEventSink source](https://github.com/serilog/serilog/blob/dev/src/Serilog/Core/IBatchedLogEventSink.cs), [BatchingOptions source](https://github.com/serilog/serilog/blob/dev/src/Serilog/Configuration/BatchingOptions.cs), [BatchingSink source](https://github.com/serilog/serilog/blob/dev/src/Serilog/Core/Sinks/Batching/BatchingSink.cs), [Serilog.Sinks.PeriodicBatching README](https://github.com/serilog/serilog-sinks-periodicbatching), [Configuration Basics wiki](https://github.com/serilog/serilog/wiki/configuration-basics), [Lifecycle of Loggers wiki](https://github.com/serilog/serilog/wiki/Lifecycle-of-Loggers)

- **Batched sink, current way**: batching is native in **Serilog core since 4.0** (latest stable **Serilog 4.4.0**, 2026-07-10). Implement **`Serilog.Core.IBatchedLogEventSink`** — `Task EmitBatchAsync(IReadOnlyCollection<LogEvent> batch)` plus optional `Task OnEmptyBatchAsync()` — and register with **`WriteTo.Sink(myBatchedSink, new BatchingOptions { ... })`**. The old **`Serilog.Sinks.PeriodicBatching` package (4.1.0) is legacy**: its own README says "New projects should use Serilog's IBatchedLogEventSink and WriteTo.Sink(IBatchedLogEventSink), not this package which is now only maintained for compatibility reasons." The batching infrastructure owns retries/diagnostics — implementations should let exceptions surface from `EmitBatchAsync`.
- **`BatchingOptions` defaults**: `BatchSizeLimit` 1000, `BufferingTimeLimit` 2 s (a batch also emits early when full), `QueueLimit` 100,000 (excess events dropped; null = unbounded), `EagerlyEmitFirstEvent` true, `RetryTimeLimit` 10 min. The 2 s default buffering matches the design's "~1-2 s" producer flush target out of the box.
- **Routing by property (DocGuid vs console)** — two idiomatic options:
  - `WriteTo.Conditional(evt => evt.Properties.ContainsKey("DocGuid"), wt => wt.Sink(queueSink))` plus a mirrored `WriteTo.Conditional(not ...)` for console — fine for simple predicate routing.
  - Sub-loggers for pipeline-level split (docs' recommendation when sinks should see different event streams): `WriteTo.Logger(lc => lc.Filter.ByIncludingOnly(Matching.WithProperty("DocGuid")).WriteTo.Sink(queueSink))` and `WriteTo.Logger(lc => lc.Filter.ByExcluding(Matching.WithProperty("DocGuid")).WriteTo.Console())`. `Matching.WithProperty` lives in `Serilog.Filters`. Sub-loggers shallow-copy events, so enrichment inside one branch doesn't leak to the other.
  - (Top-level `.Filter.ByIncludingOnly` would drop non-matching events from *all* sinks — wrong here.)
- **`Log.CloseAndFlush()` guarantees**: it disposes the root logger, which disposes the internal `BatchingSink`; disposal signals shutdown, waits for the background loop, and **flushes the entire remaining queue through `EmitBatchAsync`, waiting for in-flight batches**. Source comments: "Try flushing the rest of the queue, but bail out on any failure" and "Shutdown time is unbounded" (no timeout — but it stops retrying, so a failing target during shutdown loses that batch rather than hanging forever). Net: on graceful shutdown, every event accepted into the sink's queue gets one delivery attempt; events are lost only if the final flush attempt fails or the process is killed hard — consistent with the accepted "minimal loss, not strict" stance. In ASP.NET Core / generic host apps, `UseSerilog` disposes the logger (calling this) on host shutdown; otherwise call `Log.CloseAndFlush()` explicitly at exit.

## Verdict for the design

All load-bearing assumptions check out: 32-msg batch dequeue, 48 KiB usable payload after Base64, DequeueCount-based poison handling at 5, visibility-timeout redelivery, atomic uncoordinated appends per AppendBlock call, 50k-block cap comfortably distant. One flag: Azurite's "Concurrent Append" limitation + no-TPS-guarantee means the local sim proves *mechanics*, and its absolute drain time is a lower bound on fidelity, not a benchmark of Azure.
