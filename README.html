BlobLogOpt: the document-log pipe

Replacing the single-consumer document-log funnel with a horizontally scalable pipeline: Serilog → Azure Storage Queue → parallel consumers → per-document Append Blobs → paged read API.

2026-08-28 · .NET 10 · Aspire 13.5 · Azurite · status: all acceptance tests passed

1. The problem

Production behavior today: every log line that carries a DocGuid goes to a queue, and one single consumer writes it into that document's JSON log file by downloading, modifying, and re-uploading the whole blob. One consumer exists to guarantee ordering. At month start/end (10–20k docs/day, ~200 lines/doc) the queue backs up past 2M+ messages and takes hours-to-days to recover.

That is a funnel: a wide producer top and a fixed one-message-at-a-time bottom. The goal of this POC is a pipe: consumption capacity that scales with production, so the backlog can never form — plus fast recovery if one ever does.

2. The three moves that make it fast

1 · Ordering moved to read time

Every log record carries a timestamp plus a unique (src, seq) key. The API sorts and dedupes when the log is read. Consumers therefore need no ordering, no per-document affinity, no coordination — they scale wide.

2 · Envelope packing

~650 log lines ride in one gzip-compressed queue message (48 KiB usable after Base64). 2M lines become ~3,200 queue messages. Both enqueue and dequeue traffic shrink ~600×.

3 · Append Blob + JSON-lines

One atomic AppendBlock per document batch replaces download-modify-upload of a JSON array. Concurrent appends from many replicas are safe (atomic per call).

Move 1 is the one that matters most: the ordering rule was the entire reason for the single consumer. Once ordering is a read-time concern, the consumer count is just a throughput dial (KEDA in production).

3. Architecture

4. Wire formats

Record — one JSON line per log event

{ "ts": "2026-08-28T10:43:29.9251356Z",  // UTC ISO-8601, stamped at log time
  "level": "Information",
  "msg": "Processing step 0 of document", // rendered message text
  "ex": null,                             // full exception ToString, or null
  "docGuid": "02046204-aec3-4a01-a736-a63c153e01b8",
  "src": "829317ac",                      // random id per producer instance
  "seq": 64 }                             // per-instance counter

(src, seq) is globally unique. A document's ~200 lines come from up to 4 different services (4 different src values) over its ~2-minute lifetime — the read-time sort is what merges them into one coherent log.

Envelope — one queue message

{ "v": 1, "lines": [ ...records... ] }   →  gzip  →  Base64  →  SendMessage

Packed until the raw JSON reaches 128 KiB, which lands comfortably under the 48 KiB post-Base64 queue limit after compression. Mixed DocGuids per envelope are fine — no affinity needed.

Reader contract (any consumer of the blob files)

  1. Parse JSON-lines.
  2. Dedupe by (src, seq) — at-least-once delivery means rare replays are expected and harmless.
  3. Sort by ts ascending, tie-break by (src, seq).

5. The harness

The POC is an Aspire 13.5 distributed app using the single-file C# AppHost (apphost.cs, no .csproj). Azure Storage is emulated by Azurite in Docker with pinned host ports (blob 27000, queue 27001) so tooling can reach it directly.

ComponentWhat it is
apphost.csAspire AppHost: Azurite emulator, doc-logs + doc-logs-poison queues, doc-logs blob container, and the three projects below. All load knobs are env vars here.
src/ProducerLoad generator + the real QueueLogSink (Serilog 4 IBatchedLogEventSink). Emits N docs × M lines with realistic burstiness (~200 docs in flight) and 10% "monster" docs.
src/ConsumerThe document log handler. 4 replicas × 4 dequeue pipelines. Batch-dequeues 32 messages, groups lines by DocGuid across the whole batch, parallel-appends, then deletes messages only after every append succeeded.

tools/depth.cs, tools/verify.cs, tools/pickdoc.csSingle-file C# scripts (dotnet run tools/depth.cs): queue depth / blob count, content verification, grab a DocGuid.

7. How the read API works

EndpointBehavior
GET /api/documents?limit=25Lists DocGuids (derived from blob name prefixes; listing is sorted so prefixes dedupe adjacently).
GET /api/documents/{docGuid}/logs?page_size=25&page=1Downloads {docGuid}/log.jsonl, applies the reader contract (dedupe → sort), then pages. 404 if the doc has no logs. page_size clamped to 1–1000.

rowId is the record's position in the sorted, deduped list (1-based). Ordering is already fully deterministic without it — (src, seq) breaks timestamp ties — so rowId is a UI convenience: stable row keys, "jump to line", range selection.

Partitioning: one shared container (doc-logs); each document is a prefix: {docGuid}/log.jsonl. Production currently uses container-per-document — that also works and is a one-line path change. One container keeps lifecycle rules (e.g. auto-delete after N months) in a single place.

9. Limitations & honest caveats

Azurite is the ceiling, not Azure. Azurite is a single Node.js process; it caps the whole sim at roughly 2,500–3,000 lines/s combined (produce + consume + API). All numbers above are lower bounds on the mechanics, not Azure throughput benchmarks. Real Azure Storage targets ~2,000 msgs/s per queue — at ~650 lines/envelope that alone is ~1.3M lines/s of headroom. Azurite also lists concurrent-append support as limited, which real Azure does not.

  • Loss window: the sink buffers ~2 s in memory (Serilog batching). Graceful shutdown flushes (Log.CloseAndFlush()); a hard kill (OOM, power) can lose that window. This matches the accepted requirement ("minimal loss", not strict) and is no worse than the current async sink.
  • At-least-once, not exactly-once: a crash between append and message delete replays the batch → duplicate lines in the blob. By design; the reader dedupes by (src, seq). Consumers delete a batch's messages only after every append in the batch succeeded.
  • Append Blob 50,000-block cap: with batched appends a doc uses a handful of blocks; unreachable at ~200–2,000 lines/doc. If ever hit (HTTP 409), the planned mitigation is rolling to log-2.jsonl — noted in code, not implemented.
  • Read API loads the whole file per request: fine at ≤ a few MB per doc (a 2,000-line monster is ~500 KB). Add caching or streaming only if docs ever grow past that.
  • No auth on the API — accepted: it sits behind a private network, and the log-read API is the only piece with any external reach.

10. Gotchas we hit (so you don't)

  • Aspire keyed clients: registering an unkeyed AddAzureQueue and a keyed one nulls the unkeyed client. If a service needs two queues, register both keyed (AddKeyedAzureQueue + [FromKeyedServices]).
  • AppHost API shape: AddQueue / AddBlobContainer hang off the storage resource, not the queue/blob service builders — and a queue and a container can't share a resource name (names are global per AppHost).
  • Azurite flags: --inMemoryPersistence conflicts with the --location arg Aspire always passes; the container exits at boot. Don't use it.
  • aspire logs streams (blocks) while the app runs — poll state via the pinned Azurite ports (tools/depth.cs) instead of scraping logs.
  • Replicated resources: aspire wait consumer fails on a WithReplicas resource (replica names get random suffixes). Use aspire logs consumer or the dashboard.
  • Batching sink backpressure: Serilog's batching queue drops events when full. The generator monitors emitted-vs-sent and pauses — in production the natural log rate never approaches this, but know the queue limit exists (QueueLimit, we set 500k).

11. Porting to production — checklist

  1. Sink: lift QueueLogSink + the sub-logger routing (Filter.ByIncludingOnly(Matching.WithProperty("DocGuid"))) into your shared logging package. Requires Serilog ≥ 4.0 (batching is in core now; the old PeriodicBatching package is legacy).
  2. Consumer: the worker is a plain queue-draining service — deploy like any other KEDA-scaled deployment, scaling on queue length instead of CPU. Replica count is a pure throughput dial; replicas never coordinate.
  3. Viewer: point it at the LogApi pattern (or embed the reader contract — dedupe by (src, seq), sort by ts) instead of the old JSON array files.
  4. Decide partitioning: keep container-per-doc for parity, or move to one-container-with-prefix (recommended; one lifecycle policy).
  5. Migration is out of scope of this POC — old JSON-array files stay readable by the old path until they age out.

12. Code-review hardening (same day)

A Codex review of the full POC turned up several correctness and safety gaps. Fixed the same day, since this only ships behind a private network — the log-read API is the one piece with any external reach, and the fixes below don't depend on that boundary.

FixWhy
Bad queue message no longer kills a worker pipelineDecode/parse failures are now caught per message instead of crashing the loop that handles it. A replica silently losing one of its four pipelines, permanently, was the real risk.
Zero-length append loop fixedA single record bigger than one append chunk could make the block-splitter compute a 0-byte block and stop advancing. It now takes the whole oversized line instead of stalling.
Batch size check counts real bytesThe 128 KiB envelope cap was measured in UTF-16 characters, not UTF-8 bytes — non-ASCII content could sneak past it. Now counted correctly.
Decompressed message size capped at 16 MBGzip expansion was unbounded before. A pathological message could no longer balloon into a large in-memory buffer.
Visibility timeout: 2 min → 30 minLong enough for a normal batch to finish without another worker picking up the same message mid-flight.
Poison threshold: 5 dequeues → 2 appearancesA message gets one retry; the second failure sends it straight to doc-logs-poison instead of cycling six times first.
tools/verify.cs matches real line countsIt was still asserting the old fixed 100-line test fixture; it now checks the actual 200 / 2,000-line config and would have been silently reporting healthy runs as broken.

Left alone, on purpose: API auth — this sits behind a private network, and adding a key here would guard against a threat model that doesn't apply. Dead-letter/poison-queue handling beyond the send is still out of scope.
